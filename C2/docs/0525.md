# C2 Owner 接口联调实现报告（2025-05-25）

## 1. 接口联调实现情况

### 1.1 接口总览

C2 Owner（货主）涉及 4 条外部消息接口，已全部实现：

| 方向 | 消息名 | 状态 | 通信方式 | 说明 |
|---|---|---|---|---|
| C2 → C3 FFW | `order-to-ffw` | ✅ 已联调 | RabbitMQ | `ff.order-received` / `Message_Owner_order_received` |
| C2 → C3 Transport | `outbound-ctn-to-transport` | ✅ 已联调 | RabbitMQ | `transport.outbound-ctn-received` / `Message_Owner_Outbound_CTN_received` |
| C3 → C2 | `ctn-to-owner` | ✅ 已联调 | RabbitMQ | C3 发 `owner.empty-ctn-received`，C2 Consumer 映射为 `ctn-to-owner` |
| C5 → C2 | `expense-note-to-owner` | ✅ 已联调 | Camunda REST | C5 Worker 内直接调用 `publishMessage` |

### 1.2 C2 → C3（Outbound）实现

C2 内部保持 `lower-case-with-hyphens` 命名，通过 `outbound-adapter.ts` 统一路由：

- 若消息在 C3 映射表中 → 走 **RabbitMQ**（`rabbitmq/publisher.ts`）
- 否则 → 走 **Camunda REST** fallback

映射关系：

```
'order-to-ffw'          → camundaName: 'Message_Owner_order_received',          routingKey: 'ff.order-received'
'outbound-ctn-to-transport' → camundaName: 'Message_Owner_Outbound_CTN_received', routingKey: 'transport.outbound-ctn-received'
```

### 1.3 C3/C5 → C2（Inbound）实现

| 来源 | 接收方式 | 处理逻辑 |
|---|---|---|
| C3 Transport | RabbitMQ Consumer (`rabbitmq/consumer.ts`) | 订阅 `camunda.owner` 队列，绑定 `owner.#`；收到 `Message_Transport_empty_CTN_received` 后映射为 `ctn-to-owner`，通过 `CamundaRestClient.publishMessage()` 注入 C2 BPMN |
| C5 Shipping Agency | Camunda REST API 直连 | C5 Worker 内直接调用 `publishMessage({ name: "expense-note-to-owner", ... })`，C2 BPMN 直接捕获 |

## 2. 各种情况的启动程序及设计原因

### 2.1 启动程序清单

```bash
# 1. 生产模式：启动 C2 Workers + RabbitMQ（持续运行）
cd owner/nodejs
npx ts-node source/index.ts

# 2. 快速演示：自动创建实例 + 自动 mock 入站消息
cd owner/nodejs
npx ts-node source/demo.ts [--orderId=xxx] [--useRabbitmq=true]

# 3. 单组 E2E：自动发 mock inbound，验证 C2 内部流程
cd owner/nodejs
npx ts-node source/e2e-test.ts [--orderId=xxx] [--useRabbitmq=true]

# 4. 跨组 E2E（推荐）：等真实消息，超时自动 fallback mock
cd owner/nodejs
npx ts-node source/e2e-cross-group.ts [--orderId=xxx]

# 5. 严格跨组 E2E：无 fallback，FAIL if 未收到真实消息
cd owner/nodejs
npx ts-node source/e2e-strict.ts [--orderId=xxx]
```

### 2.2 设计原因

| 脚本 | 用途 | 为什么这样设计 |
|---|---|---|
| `index.ts` | 生产/联调常驻 | Workers + RabbitMQ Publisher/Consumer 全生命周期管理，SIGINT 优雅关闭 |
| `demo.ts` | 手动演示/调试 | 一键创建实例 + mock 入站，带 `--useRabbitmq` 开关，可快速切换通信方式 |
| `e2e-test.ts` | 单组自测 | 不依赖其他组，自动发 mock inbound，验证 C2 BPMN + Workers 自身逻辑 |
| `e2e-cross-group.ts` | 跨组联调（最常用） | **核心设计**：先等真实消息（10s timeout），收不到再 mock fallback。兼容其他组未就绪的场景，同时能验证真实链路 |
| `e2e-strict.ts` | CI/CD 严格验收 | 无 fallback，强制要求 C3/C5 真实消息到达。用于最终验收，避免 mock 掩盖真实问题 |

### 2.3 跨组 E2E 的 Phase 设计

`e2e-cross-group.ts` 按 5 个 Phase 执行：

1. **Phase 1**：等 `order-to-ffw` worker 完成（验证 C2 → C3 outbound）
2. **Phase 2**：等 C3 真实 `ctn-to-owner`（10s），超时 mock fallback
3. **Phase 3**：等 `outbound-ctn-to-transport` worker 完成（验证 C2 → C3 第二条 outbound）
4. **Phase 4**：等 C5 真实 `expense-note-to-owner`（10s），超时 mock fallback
5. **Phase 5**：轮询实例状态到 `COMPLETED`（30s timeout）

最终报告会标注每条 inbound 是 **REAL** 还是 **MOCK**，一目了然。

## 3. 还需要别的组实现的接口

**C2 自身接口已全部完成**。以下是对其他组的依赖说明（均已本地验证，需对方确认）：

### 3.1 C3 Freight Forwarder（已就绪）

- 消费 `ff.order-received`（RabbitMQ）触发 FFW 流程
- 无需额外修改，C2 已通过 RabbitMQ 联调验证

### 3.2 C3 Transport（已就绪）

- `ctn-to-owner` Worker 内通过 RabbitMQ 发送 `owner.empty-ctn-received`
- C2 Consumer 已能正常接收并映射为 `ctn-to-owner`
- ⚠️ 已知：C3 BPMN 中 `ctn-to-owner` 是 **ServiceTask** 不是 SendTask，消息发送逻辑写在 Worker 内。如需规范实现，建议后续改为 SendTask + `<bpmn:message>`

### 3.3 C5 Shipping Agency（需对方本地修改）

- `issue-expense-note-to-owner` Worker 内需要增加 `publishMessage` 调用：

```javascript
await publishMessage(config.camundaRestAddress, {
    name: "expense-note-to-owner",
    correlationKey: job.variables.orderId,
    timeToLive: 300000,
    variables: {
        orderId: job.variables.orderId,
        timestamp: nowIso(),
        senderId: "SHIPPING-AGENCY-01",
        expenseId: `EXP-${job.variables.orderId}`,
        expenseAmount: 1250.5,
        currency: "CNY"
    }
});
```

- ⚠️ 当前 C5 BPMN 中 `Task_IssueExpenseNote` 是 ServiceTask，无 `<bpmn:message>` 定义。Worker 内手动调用 `publishMessage` 为本地联调临时方案，建议后续规范化为 SendTask

### 3.4 总结：无阻塞项

所有接口在本地均已跑通。C3 无需再改代码；C5 只需在 Worker 内加一行 `publishMessage`（本地已验证）。

## 4. Debug 情况

### 4.1 已解决的问题

| 问题 | 现象 | 根因 | 解决方式 |
|---|---|---|---|
| C2 → C3 消息名不匹配 | C3 收不到消息 | C2 内部用 `lower-case-with-hyphens`，C3 期望 `Message_XXX_received` | 增加 `MESSAGE_MAPPING` 映射表（`rabbitmq/config.ts`） |
| C3 → C2 无消息返回 | `ctn-to-owner` 卡住 | C3 `ctn-to-owner` 是 ServiceTask，Worker 只 `job.complete()` 不写回 | C3 已在 Worker 内增加 RabbitMQ `publisher.publish()` 发送 `owner.empty-ctn-received` |
| C5 → C2 无消息 | `expense note received` 卡住 | C5 BPMN 无 `expense-note-to-owner` 消息定义，Worker 不发送 | C5 Worker 内本地增加 `publishMessage` 调用 |
| `Record<string, unknown>` 类型不兼容 | TS 编译报错 | `publishMessage` 期望 `IInputVariables` | `variables as any` 类型断言 |
| 变量命名不一致 | C2 mock 用 `handOverTime`，C3 发 `handoverTime` | 驼峰命名差异 | C2 Consumer 透传 variables，不影响 correlationKey 匹配 |

### 4.2 测试超时参数

| 阶段 | 超时时间 | 说明 |
|---|---|---|
| order-to-ffw | 8s | Worker 执行通常 < 3s |
| ctn-to-owner（real） | 10s（cross）/ 15s（strict） | 需等 C3 Worker 执行 + RabbitMQ 传输 |
| outbound-ctn-to-transport | 8s | Worker 执行通常 < 3s |
| expense-note-to-owner（real） | 10s（cross）/ 15s（strict） | 需等 C5 流程走到 Worker + REST 传输 |
| instance COMPLETED | 30s | 全流程总超时 |

### 4.3 当前已知 Limitation

1. **C3 `ctn-to-owner` 通过 RabbitMQ 而非 Camunda REST**：C3 Worker 内调用 `publisher.publish()` 发 RabbitMQ，C2 需启动 RabbitMQ Consumer 接收。若 RabbitMQ 未启动，C2 无法收到此消息（`e2e-cross-group.ts` 会 fallback mock）。
2. **C5 `expense-note-to-owner` 为本地临时修改**：C5 远程仓库未包含 `publishMessage` 调用，对方组员需同步此改动。
3. **混合通信架构**：C3 走 RabbitMQ，C5 走 Camunda REST，C2 需同时维护两套通道。后续如需统一，可协商全部迁移至 RabbitMQ 或全部走 REST。
